4. DevOps foundation

4.1 Repository structure (modular monolith)

One deployable API split into one project per module. A module may use only the shared kernel, never another module; architecture tests fail the build if this rule is broken. This supports the Modifiability NFR (adding a biller touches only Biller Integration and configuration).

paylink/
├── src/
│   ├── PayLink.Api/            API host: OpenAPI (Swagger), health checks, module wiring
│   ├── PayLink.SharedKernel/   IModule contract shared by all modules
│   └── Modules/                Accounts · Catalog · Payments · BillerIntegration ·
│                               Fees · Notifications · Fraud · Reconciliation
├── mocks/PayLink.MockBillers/  Mock ElectroCo / AquaCo / TopUpNet / NetCo
├── tests/
│   ├── PayLink.Api.IntegrationTests/   boots the real API in memory (3 tests)
│   └── PayLink.ArchitectureTests/      module boundary rules (4 tests)
├── .github/workflows/ci.yml   CI pipeline
├── docker-compose.yml         db + mock-billers + api
└── docs/                      requirements, design, prompt log, DevOps guide

Lessons so far

Where AI helped: scaffolding a consistent structure quickly and checking settings we could not see in the UI (P8). Where it failed: small configuration details (P3, P4) that looked right but broke tooling, and repository defaults that did not match our needs (P6). What we do now: run lint and tests locally before trusting AI output, check the test count rather than only the exit code, and write structured prompts (role, context, constraints, output format).
